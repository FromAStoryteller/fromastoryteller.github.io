# Progressive delivery and contributor media

Public discovery combines the file catalogue and the first contributor page behind one fresh-revision-gated anonymous endpoint. Further contributor pages load through an explicit button; the notice makes clear that filters and sorting cover the loaded set. Following no longer delays first content. The grid mounts 24 cards at a time with a keyboard-accessible Show more button, preserves unchanged card/image nodes, and observes image URLs near the viewport. Hidden images do not receive URLs until visible. Featured media stays eager; related catalogue work waits until its section approaches the screen. No-JavaScript card images have a noscript fallback.

Contributor cover uploads create JPEG sizes in the browser from the selected crop at quality 94, never enlarging the source. Only sizes smaller than the retained master are sent. The server bounds the files, verifies JPEG dimensions, stores immutable sibling objects and marks only successfully uploaded widths ready using service-only column access. The image gateway reads that metadata through caller-scoped RLS, serves a stored size without codecs, and falls back to the master if a size is missing. Visibility is checked again before delivery. Cleanup deletes the exact claimed master and its bounded sibling names together. Existing covers without stored sizes continue serving their master; re-upload creates the smaller versions. No automatic server-side resize is re-enabled.

Game/tool uploads preserve up to three media subfolders under assets/ in ZIP and folder imports. Client and database validators reject traversal, absolute paths, duplicate case-folded paths, executable media and oversized packages. Hosted and offline players share FAS.asset(path), FAS.image(path) and FAS.preloadImages(paths). FAS.image waits for image loading before returning a drawable object. CSS assets resolve within the isolated package and missing CSS assets fail with a useful message. Exact path/case matters. Authors must use these helpers instead of direct relative fetches in the hosted sandbox. Media bytes, pixel art and audio are preserved. Existing game account APIs and opaque sandbox boundaries remain unchanged.

## Existing-cover backfill - 29 October 2026

The existing ten production cover masters now have verified 480, 800 and 1200 pixel JPEG siblings. The development cover was rehearsed first. All eleven 1600 x 900 masters remain byte-identical. The ten production 480px versions total 292,343 bytes versus 1,732,876 bytes for the masters (83.1% less transfer when that size is selected); larger displays still select larger siblings or the master.

`scripts/prepare-cover-backfill.mjs` prepares sizes offline with the same browser quality-94 generator as new uploads. Supply a JSON array containing `project` (`dev` or `prod`), asset `id`, `pixel_width`, `pixel_height` and a basename-only `masterFile`, all stored alongside that inventory. The script verifies each master's dimensions, refuses enlargement, and writes derivatives plus `prepared.json` with SHA-256 hashes. It has no network or Storage writes. Install the same Playwright version used by the browser CI before running it.

An operator may deploy `_shared/cover-backfill.mjs` behind JWT verification with an explicit asset/path inventory, a hash of a randomly generated 256-bit operator token, and a short expiry. The entrypoint must take its project URL and service role from server environment variables; neither belongs in a client or inventory. This helper permits only reading listed masters and creating their bounded JPEG siblings. It never enables upsert or updates application metadata. Existing differing objects fail safely; retries of identical bytes are allowed. Every uploaded object is read back and checked against its prepared hash.

Only after all sizes verify, enable `derivative_widths` in a transaction guarded by the unchanged asset IDs/paths, empty previous widths, verified-master flags, and exact Storage sibling names, JPEG content types and byte lengths. Assert the expected updated-row count and roll back on any mismatch. The existing asset trigger changes the public cache revision automatically. Compare all live width responses to the prepared hashes, and compare original delivery to the master hashes. Existing visibility checks and exact-sibling cleanup remain in force. For rollback, clear only the newly enabled width metadata in a guarded transaction; master delivery resumes without modifying any master bytes.

Both one-off `fas-cover-backfill-once` deployments were replaced with unconditional HTTP 410 responses after verification. No active backfill read/write capability remains. New uploads continue generating sizes automatically; no scheduled resize service or request-time codec was introduced.
